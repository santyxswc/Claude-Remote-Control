# F1: Installation and pairing

## Objective

Leave the bot configured and exactly one Telegram account authorized: `init` validates and stores
the BotFather token, `pair` links the owner's Telegram account to this PC with a one-time code
confirmed at the terminal, and `access list` / `access revoke` manage the allowlist. Messages from
anyone else are dropped without a reply.

## Steps

1. **State.** `src/adapters/storage/stateDir.ts` resolves the state directory
   (`TELEGRAM_BRIDGE_HOME`, else `<CLAUDE_CONFIG_DIR or ~/.claude>/channels/telegram-bridge`),
   created 0700. It holds:
   - `.env` with `TELEGRAM_BOT_TOKEN=...` (0600). The environment variable of the same name
     overrides it.
   - `bot.json` with the bot id and username from `getMe` (not secret).
   - `bridge.sqlite` (0600, WAL, busy timeout, migrations by `PRAGMA user_version`): tables
     `allowed_senders`, `pairings`, `audit_log` (append-only, enforced by triggers) and
     `poller_lock`.
2. **Domain.** `Pairing` is a state machine (`pending -> claimed -> confirmed`, plus `expired` and
   `cancelled`); invalid transitions throw. Codes are 16 random bytes in base64url (22
   characters), valid 120 s, single use; 5 failed attempts cancel the pairing; a claim must be
   confirmed within 5 minutes. Only the SHA-256 of the code is stored, and it is dropped when the
   pairing ends.
3. **Use cases** (`src/application/use-cases/`): `InitBot`, `StartPairing`, `ClaimPairing`,
   `AwaitPairingClaim`, `ConfirmPairing`, `ListAllowedSenders`, `RevokeSender`,
   `AuthorizeSender`. Every state change is audited.
4. **Inbound chain** (`src/application/pipeline/`): private-chat gate, pairing claim
   (`/start <code>`), authentication by `from.id`, and a terminal step that discards until F2.
5. **Telegram** (`src/adapters/telegram/`): grammY long polling restricted to `message` updates;
   401/404 stop polling, a persistent 409 stops after backed-off retries, other errors retry.
   Errors are logged only as redacted summaries.
6. **Single poller** (ADR 0006): the channel polls while it holds the lock row; `pair` polls
   only when nobody else does.
7. **CLI** (`src/cli.ts`, `bin` `telegram-bridge`, script `bun run bridge -- <cmd>`): `init`,
   `pair`, `access list`, `access revoke <id>`, `--help`. Exit codes: 0 ok, 1 failure, 2 usage.
   Output in Spanish by default; `TELEGRAM_BRIDGE_LOCALE=en` for English.
8. **Channel** (`src/main.ts`): with a token it opens the database and polls under the lock;
   without one it logs a single hint and keeps serving MCP.

## Acceptance

- A second Telegram account writes to the bot and nothing happens: no reply and no event in the
  session. Automated in `tests/acceptance/F1.test.ts` with the real poller, SQLite, hasher and
  gateway against an in-process fake of the Bot API: the stranger's messages (plain text,
  `/start`, a wrong code, the already used code) produce zero `sendMessage` calls and zero
  session events, while the paired owner's message gets through. The log keeps the stranger's id
  and never the text, the code or the token.
- `bun run check` passes (lint, typecheck, architecture, tests) on Ubuntu and Windows.

## Sequence

```mermaid
sequenceDiagram
    actor O as Owner (terminal)
    participant CLI as pair (CLI process)
    participant DB as bridge.sqlite
    participant CH as Channel process
    participant TG as Telegram
    actor P as Owner (phone)

    O->>CLI: telegram-bridge pair
    CLI->>DB: tryAcquire poller lock (cli)
    alt a live channel process holds the lock
        DB-->>CLI: held by channel
        Note over CLI,CH: the channel keeps polling; the CLI only watches the database
    else nobody holds it
        DB-->>CLI: acquired
        CLI->>TG: getUpdates (long polling, heartbeat every 10 s)
    end
    CLI->>DB: replace active pairing, insert pending (SHA-256 of code)
    CLI-->>O: QR + https://t.me/<bot>?start=<code> (expires in 120 s)
    P->>TG: opens link, sends /start <code>
    alt channel mode
        TG-->>CH: update
    else CLI mode
        TG-->>CLI: update
    end
    Note over CLI,CH: whoever polls runs the inbound chain (shown for the channel):<br/>private chat? then /start code? then constant-time compare
    alt code matches
        CH->>DB: pending -> claimed (sender id, @username, name)
        CH->>TG: sendMessage "confirm in your terminal"
    else wrong code
        CH->>DB: failed attempts + 1 (5 -> cancelled), no reply
    end
    loop every 500 ms until claimed, expired or cancelled
        CLI->>DB: read pairing
    end
    CLI->>TG: stop polling, confirm offset (CLI mode only)
    CLI->>DB: release lock (CLI mode only)
    CLI-->>O: "Code received from: Name (@user), id 123"
    O->>CLI: confirm y/N
    alt yes
        CLI->>DB: claimed -> confirmed, add allowed sender, audit
    else no
        CLI->>DB: claimed -> cancelled (declined), audit
    end
```

## Manual verification (owner, once a BotFather token exists)

Use a throwaway state directory first so nothing touches the real one:

```powershell
$env:TELEGRAM_BRIDGE_HOME = "$env:TEMP\tb-f1"   # bash: export TELEGRAM_BRIDGE_HOME=/tmp/tb-f1
```

1. **init.** `bun run bridge -- init`, paste the token (nothing is echoed). Expect
   `Listo: el bot @<name> quedó configurado.` Check that `.env` and `bot.json` exist in the state
   directory; on Linux `ls -l` shows `-rw-------` for `.env` and `bridge.sqlite`, `drwx------`
   for the directory. A wrong token prints the rejection message and saves nothing. Also try
   `Get-Content token.txt | bun run bridge -- init --token-stdin` (bash: `... < token.txt`).
2. **pair without a session.** `bun run bridge -- pair`. Expect a QR code, the link, "vence en
   120 segundos" and "Esperando el código en Telegram...". Scan with the phone and press Start.
   The phone gets "Código recibido. Confirma el emparejamiento en la terminal..."; the terminal
   shows your name, @username and numeric id. Answer `s`. `bun run bridge -- access list` shows
   the account.
3. **pair with a session running.** Start the channel
   (`claude --dangerously-load-development-channels server:telegram-bridge`) and check its stderr
   (or `claude --debug`) for `telegram polling started`. In another terminal run `pair`: it prints
   "La sesión de Claude Code está recibiendo los mensajes del bot..." and the claim arrives
   through the channel process. Decline with `n` once to check that nobody is added.
4. **The acceptance check.** From a second Telegram account, write to the bot: plain text,
   `/start`, `/start somethingwrong`. Expect no reply at all and nothing in the Claude Code
   session; the channel's stderr shows `dropped message from an unauthorized sender` with that
   account's id and no message text.
5. **Expiry and attempts.** Run `pair` and wait 2 minutes: "El código venció...". Run `pair`
   again and send five wrong `/start` codes from the second account: the pairing is cancelled.
6. **revoke.** `bun run bridge -- access revoke <id>`; the account's messages are dropped again.
7. **Logs.** Search the channel's stderr and the terminal output for the token: it must not
   appear. This shows the audit trail, which must contain no codes or tokens:

   ```powershell
   bun -e 'import { Database } from "bun:sqlite"; console.log(new Database(Bun.argv.at(-1), { readonly: true }).query("select * from audit_log").all())' "$env:TELEGRAM_BRIDGE_HOME\bridge.sqlite"
   ```
8. **No token.** With an empty state directory, start a session: the server stays connected in
   `/mcp` and logs `telegram is not configured; run ...` once.

Afterwards remove the throwaway directory and unset `TELEGRAM_BRIDGE_HOME`, then repeat `init`
and `pair` for real.
