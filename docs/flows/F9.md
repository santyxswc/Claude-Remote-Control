# F9: Pinned status message

## Objective

A glance at the chat shows what the session is doing, without asking. `/pin` creates one pinned
message per chat, and the bridge edits it in place as the session works. Its content comes only
from hook events and the bridge's own state, never from text Claude writes (ADR 0013). It is off
until `/pin`. Plan acceptance: a pinned message that follows the session, with no notification
for each change.

## Steps

1. **Content** (plain text, one message, sanitized, redacted in `buildOutbound()`):

   ```
   📌 Claude Code · my-app
   State: working since 14:05
   Last tool: Bash · Run the unit tests
   Waiting for you: 1 permissions, 0 questions
   Last finished: 13:58
   ```

   - **State** is one of `unknown (no hook events yet)`, `idle since`, `working since`,
     `waiting for your answer [since]`, `braked since … (/resume releases it)` or
     `session ended since`.
     - Priority order: ended, then braked (from the brake flag), then waiting (an attention
       `Notification`, or any open permission request or `ask_choice` question of this
       session), then what the hooks said.
     - "Working since" is when the turn began, and is kept after the owner answers a question
       mid-turn.
     - Times are the PC's local `HH:MM`.
   - **Last tool** is the tool name, plus:
     - for `Bash`/`PowerShell`, the hook's `description` (Claude Code's one-line summary of the
       command), up to 60 characters;
     - for `Read`/`Write`/`Edit`/`MultiEdit`/`NotebookEdit`, the file's base name;
     - nothing for other tools.

     It is never the command, a pattern, a URL or file content. It is cleared when the turn
     ends.
   - **Waiting for you**, shown only when something is open.
   - **Last finished**: the last `Stop`.
   - **Project**: the directory name of `CLAUDE_PROJECT_DIR` (or the working directory), else
     the last hook `cwd`.
   - **No todo list.** See "The todo list" below.
2. **Feed** (`HookEventRouter`, existing events only; `hooks/hooks.json` is unchanged):
   - `UserPromptSubmit` is `turn_started`.
   - `PostToolUse` is `tool_ran` with `summarizeToolUse`.
   - `Notification` of an attention type (`permission_prompt`, `idle_prompt`,
     `elicitation_dialog`) is `attention`.
   - `Stop` is `turn_ended`.
   - A forwarded chat message counts as work only once hooks are known to reach the bridge.

   The hook projection (`src/adapters/ipc/hookPayload.ts`) now forwards only an allowlist of
   `tool_input` fields: `command`, `file_path`, `notebook_path`, `url`, `pattern`, `path`,
   `description`, each cut to 1 KiB. It used to forward the first 16 top-level string fields,
   whatever they were; now file contents (`content`, `old_string`, `new_string`) and other
   fields never leave the hook process. The F4 identifying fields are a subset of the list. The brake
   `PreToolUse` hook is untouched, and no second `PreToolUse` hook was needed.
3. **Ports.**
   - `StatusMessageGateway`: `sendStatus` (silent, no preview), `editStatus`, `pinStatus`
     (silent) and `unpinStatus`.
   - The Telegram adapter makes one attempt per call. A 429 throws `StatusFloodWaitError`, and a
     deleted message throws `StatusMessageGoneError`. It never sleeps.
   - `StatusMessageStore` persists the message id: SQLite migration 4, table `status_messages`,
     one row per chat, digit-only ids.
4. **Update policy** (`src/domain/status/StatusUpdatePolicy.ts`, pure, fake-clock tests):
   - A trailing debounce of 2 s; a status that keeps changing still goes out 10 s after its
     first change.
   - At most one edit per chat every 5 s.
   - A global budget across chats: a burst of 10, then one every 3 s.
   - An unchanged render is never sent, so there is no "updated at" heartbeat.
   - Only the latest render per chat is kept.
   - A 429 holds back every chat (the limit is the bot's) until `retry_after`.
   - Any other failure keeps the render and waits the interval.
5. **Use cases.**
   - `PinStatusMessage` (`/pin`): unpins and forgets the previous message, sends the status
     silently, stores it, pins it silently, and audits `status.pinned`. "Sent but not pinned"
     still updates.
   - `UnpinStatusMessage` (`/unpin`): forgets the message first, so updates stop even if the
     unpin call fails, audits `status.unpinned`, then unpins.
   - `UpdateStatusMessages.tick()` runs every second on its own timer, never in the inbound
     lanes (M1). Only the polling process ticks.
     - It renders once and drops chats that are no longer allowlisted.
     - It asks the policy and edits what is due.
     - A message that is gone is recreated and pinned once; if that one goes too, the chat is
       dropped until the next `/pin`.
   - `finish()` runs when the channel stops while it still polls. It makes one best-effort
     "session ended" edit per message, bounded to 1 s in `inbound.stop()`. It is skipped when
     another process took the poller, because the messages are then that process's.
     `resume()` runs when polling starts again.
6. **Commands.** `/pin` and `/unpin` are listed in `/help`; they are not urgent.

### The todo list

It is left out, because hooks do not reliably expose it.

- The Claude Code hooks reference (code.claude.com/docs/en/hooks, 2026-11-14) documents
  `TaskCreated` and `TaskCompleted` events with `task_id`, `task_subject` and an optional
  `task_description`, and says: "In a session without the Task tools, this event doesn't fire."
- The tools reference says: "The task-tracking tools, `TaskCreate`, `TaskGet`, `TaskUpdate`,
  `TaskList`, and `TodoWrite`, are available by default only on Opus 4.7, Sonnet 4.6, Haiku 4.5,
  and earlier models … On every other model, Claude Code leaves the tools out unless you opt in."
- There is no event for a task's "in progress" state.
- `task_subject` is model-written text, which goes against "fed by hooks, not by Claude".

A list that exists on some models only, cannot show what is in progress, and is written by Claude
would mislead more than it helps. The last tool and the state carry the useful part.

### Telegram facts used

- `pinChatMessage` `disable_notification`: "Notifications are always disabled in channels and
  private chats". It is passed anyway.
- `editMessageText` text is 1-4096 characters.
- The bots FAQ: "avoid sending more than one message per second" in a single chat, or 429s
  follow.

Fetched 2026-11-14 (Bot API 10.4, core.telegram.org/bots/faq).

## Acceptance

- `tests/acceptance/F9.test.ts` uses the real composition, with hook events handed to the
  listener, a fake clock and the status timer ticked by hand. It runs against the fake Bot API,
  which now handles `pinChatMessage` and `unpinChatMessage`.
  - `/pin`: one silent message without buttons, plus a silent pin. The id is stored, and there
    is no other reply.
  - A burst of hook events (prompt, three edits, a Bash call, with a token in the prompt, the
    command and the edit) produces **one** edit with the latest state. It shows the Bash
    description redacted, and neither the command nor the token reaches the fake API.
  - A minute of ticks without changes: no edit. `Stop`: one edit to idle with the finish time.
  - A restart keeps the message id. The shutdown edit says "session ended", and the next start
    edits the same message.
  - A deleted message is recreated and pinned once; the second loss stops updates quietly.
  - `/unpin` unpins, replies, and no edits follow. A stranger cannot pin.
  - A 429 on an edit does not delay `/stop`, and no edit retries during the flood wait.
- Unit tests:
  - the update policy (debounce, max wait, interval, global budget, flood wait, failures, no
    heartbeat);
  - the session log;
  - the tool summary (never a command, sanitized, capped);
  - rendering in English and Spanish;
  - redaction and fitting in `RedactingStatusGateway`;
  - pin/unpin/update (replace, failures, gone twice, allowlist removal, polling only, finish);
  - the router feed (no prompt or command text);
  - the payload projection allowlist;
  - the SQLite store and migration;
  - the Telegram gateway (silent send and pin, 429 as one attempt, "not found" as gone);
  - the commands and `/help`.
- `bun run check` passes.

## Sequence

```mermaid
sequenceDiagram
    actor P as Owner (phone)
    participant IN as Inbound chain
    participant PIN as PinStatusMessage
    participant H as Hooks (UserPromptSubmit, PostToolUse,<br/>Notification, Stop)
    participant B as StatusBoard
    participant U as UpdateStatusMessages (1 s timer)
    participant POL as StatusUpdatePolicy
    participant OUT as buildOutbound (redact, one message)

    P->>IN: /pin
    IN->>PIN: execute(chat)
    PIN->>OUT: sendStatus (silent) + pinStatus (silent)
    PIN->>PIN: store message id (SQLite)
    H->>B: turn_started / tool_ran(Bash · description) / attention / turn_ended
    loop every second (polling process only)
        U->>B: render()
        U->>POL: observe(chat, text); due?
        alt changed, settled, interval and budget allow
            U->>OUT: editStatus(ref, text)
        else 429
            OUT-->>U: StatusFloodWaitError
            U->>POL: floodWait(until): nothing else waits
        else message deleted
            U->>OUT: sendStatus + pinStatus (once)
        end
    end
    Note over U: channel stops while polling: one "session ended" edit (best effort, at most 1 s)
```

## Manual verification (owner, with a token and a paired account)

Use the throwaway state directory from `docs/flows/F1.md`, with the plugin (or the F4 hooks
snippet) installed so hook events reach the channel.

1. `/pin`: a message appears and is pinned at the top of the chat. **Record whether the phone
   buzzed** for the message or the pin (expected: neither).
2. Ask Claude to do something with a few tool calls. Within a few seconds the pinned message says
   "working since HH:MM" and "Last tool: …", changing at most every 5 s. A shell command shows its
   description, never the command.
3. When a permission prompt appears, the state says "waiting for your answer" and "Waiting for
   you: 1 permissions". Answer it.
4. When the turn ends: "idle since HH:MM" and "Last finished: HH:MM". Leave it a few minutes: the
   message is not edited again ("edited" stays put).
5. `/stop`: "braked since HH:MM". `/resume`: back.
6. Delete the pinned message by hand, then make Claude work: a new one is sent and pinned once.
   Delete that one too: no third message.
7. `/pin` again, then exit Claude Code: the message ends with "session ended". Start it again and
   work: the same message is edited.
8. `/unpin`: unpinned, "no longer updated", and nothing changes after that.
9. **[All]** Record whether an `editMessageText` on a pinned message adds any "edited" marker
   or notification.

## Open points

- **Needs live verification**:
  - that no notification fires for the silent message, the pin and the edits;
  - how a pin looks in a private bot chat;
  - how often Telegram returns 429 for edits at this pace.
- The status message is activity metadata in a chat that is not end-to-end encrypted: project
  name, tool names, file base names and command descriptions (threat model).
- Without hooks, the state stays "unknown", and the brake and pending counts still show.
- A crash leaves the last state on screen until the next start edits it.
- With two sessions, only the polling one edits (F14 changes the routing).
