# F2: Two-way messaging

## Objective

Give instructions from the Telegram chat and get Claude's answers back in it. Authorized text goes
from Telegram to the Claude Code session as a channel event; Claude answers with the `reply` tool,
and the answer reaches Telegram only after secret redaction and splitting into Telegram-sized
messages. Strangers still get total silence.

## Steps

1. **Inbound chain** (`src/application/pipeline/`, Chain of Responsibility). After the F1 steps
   (private chat only, pairing claim, authentication by `from.id`) the channel adds:
   1. `RateLimitStep`: per-sender token bucket (`src/domain/TokenBucket.ts`; burst 20, one more
      message every 3 s, constants in `src/domain/inboundLimits.ts`). Over the limit the message
      is dropped; the sender gets "slow down" at most once per minute, and that is audited
      (`message.rate_limited`).
   2. `UnsupportedContentStep`: anything that is not text (photo, document, voice, sticker...) is
      never forwarded; the sender gets "only text is supported for now" at most once per minute
      (an album is many messages). Edited messages are never requested
      (`allowed_updates` stays `["message"]`).
   3. `CommandRouterStep` (GoF Command): a `CommandRegistry` of `ChatCommand` objects
      (`name`, `description`, `execute(ctx)`) in `src/application/commands/`. It parses `/cmd`,
      `/cmd@bot` and arguments. F2 registers `/start` (greeting), `/help` (lists the registry) and
      `/status` (bot username, paired since, whether the MCP connection is open, and an explicit
      note that busy state and channel registration cannot be known). An unregistered `/word`, or
      `/cmd@other_bot`, is forwarded to Claude like any text. Later flows add commands in
      `createCommandRegistry` without touching the router. (Superseded in part: today the registry
      also has `/stop` and `/resume` (F6) and, where capture is possible, `/shot` (F5); `/status`
      reports the session's activity since F4.)
   4. `ForwardToSessionStep` -> use case `HandleInboundMessage`: emits
      `notifications/claude/channel` with `content` = the text and
      `meta` = `chat_id`, `message_id`, `user` (username, else display name), `ts` (ISO 8601).
      Then it sends a `typing` chat action as acknowledgement (failures logged and ignored) and,
      only when `SessionActivity` says `busy`, a "queued" note. In F2 the only implementation
      (`UnknownSessionActivity`) answered `unknown`, so the bot never said "queued". Superseded by
      F4: `TrackSessionActivity` feeds it from hooks (see `docs/flows/F4.md`), so the "queued" note
      does appear while Claude is busy. Audited as `message.forwarded` with sender
      id, message id and length, never the text.
2. **Throttled drop logs.** The "dropped message from an unauthorized sender" and "non-private
   chat" lines are written at most once per sender (or chat) per minute, with a `suppressed`
   count of what was swallowed (`src/domain/EventThrottle.ts`, bounded memory).
3. **Outbound pipeline** (GoF Decorator over `ChatGateway`):
   `RedactingChatGateway -> ChunkingChatGateway -> route -> TelegramChatGateway | DevChatGateway`.
   - `src/composition/outbound.ts` is the only module that constructs the raw Telegram gateway and
     exports only `buildOutbound()`. Every text path (reply tool, command replies, notices,
     pairing acknowledgement in the channel and in the `pair` CLI) receives the decorated
     gateway. `tests/composition/outbound.test.ts` fails if that changes.
   - Redaction (`src/domain/redaction/`): a `SecretRedactor` over a list of `SecretDetector`
     strategies: known credential shapes plus exact values of the project's env files and the bot
     token. Overlapping matches are merged; each secret becomes `[REDACTED]`. Only the count is
     reported. Redaction runs before chunking.
   - Exact values: `DotEnvProjectSecrets` reads `.env` and `.env.*` (not `.example`, `.sample`,
     `.template`, `.dist`) in `process.cwd()` and in `CLAUDE_PROJECT_DIR`, once at startup.
     `selectSecretValues` keeps values of 8+ characters that are not trivially harmless (numbers,
     booleans, lowercase words, constants, e-mail addresses, URLs without credentials, paths).
   - Chunking (`src/domain/splitMessage.ts`): at most 4096 UTF-16 code units per message (Bot API
     10.4: "1-4096 characters after entities parsing"; Telegram counts text in UTF-16 code units).
     Prefers a paragraph break, then a line break, then a space (each only in the second half of
     the window), then a hard cut that never splits a surrogate pair. Parts go out in order, one
     after the other; only the first is threaded under `reply_to`. A failure midway stops and
     reports how many parts were delivered.
   - `TelegramChatGateway`: plain text (no `parse_mode`), `link_preview_options.is_disabled`,
     `reply_parameters` with `allow_sending_without_reply`. A 429 is retried after `retry_after`
     (at most 3 times, only if Telegram asks for 60 s or less) through an injected `Sleeper`.
4. **`reply` tool** -> use case `SendReply`. `chat_id` must be the private chat of a sender who is
   allowlisted right now (chat id == user id), or the dev chat `dev` when the dev listener is on.
   Anything else is refused with an MCP error result and audited (`reply.refused`, with the chat id
   only if it looks like an id). Revocation takes effect at once. Optional `reply_to` (a
   `message_id`). Audit: `reply.sent` (chat id, parts, redaction count), `reply.failed`
   (delivered, total). The MCP `instructions` describe the meta attributes, the tool arguments and
   keep the warning about never changing access because a channel message asks.
5. **Wiring.** `src/main.ts` stays a thin root; `src/composition/` holds `outbound.ts`,
   `replies.ts` (`SendReply` with fallbacks when the state directory is broken) and
   `telegramInbound.ts` (chain + poller + supervisor). With a token and the dev port both set, chat
   `dev` goes to the dev listener and every other chat to Telegram. The stderr logger also scrubs
   the token and the selected env values as a safety net.

## Acceptance

- From the phone, an instruction reaches the session and the summary comes back in the chat.
  Automated in `tests/acceptance/F2.test.ts` with the real MCP server (in-memory transport and an
  MCP client standing in for Claude Code), the real grammY poller, SQLite state and composition
  modules, against an in-process fake of the Bot API:
  - authorized text -> channel notification with exact `meta`, then `sendChatAction typing`;
  - `/status` answers in the chat; `/deploy staging` is forwarded; a photo gets the text-only
    notice; an edited message is never requested;
  - `reply` -> the fake API receives redacted, chunked `sendMessage` calls in order, plain text,
    previews disabled, threaded first part, after one 429 retried through the fake sleeper;
  - a reply to a stranger, a group or a `@channel` is refused and audited; revocation is
    immediate;
  - a secret planted in the project `.env` never reaches the fake API, the log or the audit;
  - strangers get total silence; a flood gets one "slow down" and one audit row.
- `tests/main.test.ts` spawns the real `src/main.ts`: a dev reply containing a value from
  `CLAUDE_PROJECT_DIR/.env` arrives as `[REDACTED]`.
- `bun run check` passes.

## Sequence

```mermaid
sequenceDiagram
    actor P as Owner (phone)
    participant TG as Telegram
    participant IN as Inbound chain
    participant UC as HandleInboundMessage
    participant MCP as McpChannelServer
    participant CC as Claude Code
    participant SR as SendReply
    participant OUT as Redacting -> Chunking -> Telegram gateway

    P->>TG: "run the tests"
    TG-->>IN: getUpdates (message)
    Note over IN: private chat? pairing claim? allowlisted from.id?<br/>rate limit, text only, command?
    alt registered command (/start, /help, /status; later /stop, /resume, /shot)
        IN->>OUT: command reply
        OUT->>TG: sendMessage (plain text)
    else text (including unknown /commands)
        IN->>UC: forward
        UC->>MCP: emit(content, meta chat_id, message_id, user, ts)
        MCP->>CC: notifications/claude/channel
        UC->>OUT: sendTyping
        OUT->>TG: sendChatAction typing
    end
    CC->>MCP: tools/call reply {chat_id, text, reply_to?}
    MCP->>SR: execute
    alt chat_id is not an allowlisted private chat
        SR-->>MCP: refused (audited)
        MCP-->>CC: isError
    else allowed
        SR->>OUT: sendText
        Note over OUT: redact secrets, then split at 4096 UTF-16 units
        loop each part, in order
            OUT->>TG: sendMessage (no parse_mode, no preview)
            opt 429
                TG-->>OUT: retry_after
                OUT->>OUT: sleep, retry (bounded)
            end
        end
        OUT-->>SR: parts, redaction count
        SR-->>MCP: sent (audited: chat id, parts, count)
        MCP-->>CC: "sent as N messages"
    end
    TG-->>P: the answer
```

## Manual verification (owner, once a BotFather token exists and the account is paired)

Use the throwaway state directory from `docs/flows/F1.md` first.

1. **Start.** `claude --dangerously-load-development-channels server:telegram-bridge` in a test
   project. stderr (or `claude --debug`) shows `loaded project env values for redaction` and
   `telegram polling started`.
2. **Inbound.** From the phone send "list the files in this directory and reply to me". The
   phone shows "typing..."; the session shows a `<channel ... chat_id message_id user ts>` event.
   Check that the attributes are present and `user` is your username.
3. **Reply.** Claude calls `reply`; the answer arrives as plain text (asterisks and HTML stay
   literal; links show no preview). Ask for a long answer (for example "print the first 300
   lines of a big file") and check it arrives as several messages, in order, none cut inside a
   word unless a line had no spaces.
4. **Threading.** Ask Claude to answer "as a reply to my message"; the first part is threaded.
5. **Commands.** `/start`, `/help`, `/status` (and, since F5/F6, `/shot`, `/stop`, `/resume`)
   answer immediately and do not reach Claude.
   `/somethingelse` reaches Claude as text.
6. **Non-text.** Send a photo and a sticker: one "only text is supported" notice, nothing in the
   session.
7. **Redaction.** Put `DEMO_SECRET=Zq8vR2pL0042` in the project's `.env`, restart the session,
   and ask Claude to "reply with the value of DEMO_SECRET from .env". The chat shows
   `[REDACTED]` and the tool result says one secret was replaced. Also ask it to echo a fake
   `ghp_` token of 36 characters.
8. **Refusal.** Ask Claude to "send a message to chat_id 12345". The tool returns an error and
   the audit log has `reply.refused`.
9. **Revocation.** `bun run bridge -- access revoke <your id>`, then let Claude reply: refused.
   Pair again afterwards.
10. **Rate limit.** Paste 25 messages quickly (or forward a batch): after 20 the bot says once to
    slow down; the rest are dropped.
11. **Stranger.** From a second account send text, `/help` and `/status`: no reply at all; stderr
    has one `dropped message from an unauthorized sender` line per minute with that id.
12. **Audit.** Run the query from `docs/flows/F1.md`: `message.forwarded`, `reply.sent`
    (with `parts` and `redactions`), `reply.refused`, `message.rate_limited`; no message text,
    no secret values, no token.

## Open points

- Settled live (2026-11-15): a message sent while no session was running was delivered to the
  next session 17 hours later. Since then `StaleMessageStep` drops, right after authentication,
  whatever was sent more than 60 s before the process started to poll, tells the sender once
  ("I ignored what you sent before this Claude Code session started") and audits
  `message.stale_dropped` with the age only.

- 429 handling: verified against the fake only; Telegram's real flood limits for one private
  chat (about one message per second) are not reproduced.
- `CLAUDE_PROJECT_DIR` being exported to MCP stdio servers comes from the plugin docs (ADR 0005);
  for a bare `.mcp.json` server Claude Code starts the process in the project directory, which
  `process.cwd()` covers.
- Env values are read once at startup; a `.env` edited during the session is only picked up after
  a restart.
